# Rollcall QR Attendance

A compact, server-validated QR attendance system using Google Sheets as storage.

## What is included

- Multiple independent admin accounts stored in SQLite, with email OTP verification and password recovery.
- Student check-in with name and batch plus an optional email address for attendance updates.
- The first browser/device used for a student's attendance is linked to that student and can be reused for other subjects; another device is rejected.
- Server-side course mapping, Asia/Kolkata date/time, validation, duplicate protection, and signed 30-minute QR sessions.
- Ten subject tabs, a roster-driven absent finalization action, and a synchronized `Percentage` tab.
- Subject sheets show one consecutive date column per day from the first recorded date through today, newest first. Sundays and configured holidays are marked `Holiday`. Other dates with no attendance remain blank; when attendance is finalized for a class day, unmarked roster cells become `Absent`. Blank dates and holidays are excluded from attendance totals and percentages.
- Responsive instructor dashboard and mobile-first student page.

## 1. Create the Google spreadsheet

Create one spreadsheet and add these tabs exactly:

- `Students`
- `Percentage`
- `Subject 1` through `Subject 10`

Use these headers in `Students`:

```text
Student ID | Student Name | Batch | Email
```

The app automatically adds a new student to this tab the first time that student marks attendance. The `Student ID` is generated by a Google Sheets formula, not by the server. Existing students are matched by name and batch, so duplicate roster rows are not created. The app adds an optional `Email` column to the roster; emails are used only for notifications and summaries. Subject tabs continue to use their existing attendance layout. Only P1-P10, J1-J10, and D1-D10 are accepted. Use these headers in every subject tab:

```text
Date | Time | Student Name | Batch | Course | Subject | Status | Attendance Source | Session ID
```

Use these headers in `Percentage`:

```text
Student Name | Batch | Course | Subject | Attended Classes | Total Classes | Subject Percentage | Full-Course / Overall Percentage
```

Share the spreadsheet with the Google service-account email as **Editor**, then copy the spreadsheet ID from its URL.

## 2. Configure and run

```powershell
Copy-Item .env.example .env
```

Edit `.env`:

- `JWT_SECRET`: a random secret of at least 32 characters used to sign session cookies. Required in production; local development generates an ephemeral value if omitted.
- `DATABASE_URL`: SQLite database file path; defaults to `./data/attendance.sqlite`. Keep the data directory on persistent storage.
- `DEVICE_LOCKS_PATH`: optional device-lock JSON path. Set it to persistent storage when deploying (for example `/var/data/.device-locks.json`) so student device bindings survive redeploys.
- `SMTP_HOST`, `SMTP_PORT`, `SMTP_SECURE`, `SMTP_USER`, `SMTP_PASSWORD`, `SMTP_FROM`: SMTP delivery-service settings. `SMTP_USER` is the sender account, not an admin identity. `SMTP_FROM` is the sender email address; outgoing email displays "Attendance Management System" as the sender name. Use your provider's app password. The app logs a clear warning if email delivery is not configured; SMTP credentials remain server-side.
- `GOOGLE_SPREADSHEET_ID`: spreadsheet ID.
- `GOOGLE_SERVICE_ACCOUNT_JSON`: the full service-account JSON on one line.
- `APP_URL`: the URL used in QR codes. For local phone scanning, keep the phone and computer on the same Wi-Fi network; if `APP_URL` is `localhost`, the app automatically substitutes the computer's LAN IPv4 address. For scanning from another network, set this to the app's public HTTPS URL.
- `MIN_ATTENDANCE_PERCENTAGE`: optional minimum threshold for the student attendance warning. Defaults to `75`.

Generate a private value for `JWT_SECRET` with:

```powershell
node -e "console.log(require('node:crypto').randomBytes(32).toString('hex'))"
```

Put the generated value in `.env` as `JWT_SECRET`. Do not share or commit it.

For Gmail, enable 2-Step Verification on the sender account and create an App Password. Set `SMTP_HOST=smtp.gmail.com`, `SMTP_PORT=587`, `SMTP_SECURE=false`, `SMTP_USER` and `SMTP_FROM` to that sender address, and `SMTP_PASSWORD` to the App Password. For other providers, use their SMTP host, port, TLS mode, and sender credentials. Do not use the administrator or student's email as the SMTP login.

To create a structure-only copy before moving the app to a new Google Spreadsheet file:

```powershell
$env:SOURCE_GOOGLE_SPREADSHEET_ID = "current-spreadsheet-id"
$env:NEW_SPREADSHEET_NAME = "Rollcall Attendance Copy"
npm run migrate:sheet
```

The command creates a native Google Sheets copy, preserving tabs, colors, formulas, filters, validations, column widths, and formatting. It clears all rows below the first row, so old attendance records and roster data are not carried over. Copy the new ID printed by the command into `GOOGLE_SPREADSHEET_ID`, then restart the app. The service account must have access to the source spreadsheet and permission to create a copy in Google Drive.

Then run:

```powershell
npm install
npm start
```

The default port is `3000`. If you see `EADDRINUSE`, the app is already running on that port; use `http://localhost:3000` instead of starting a second copy. To run another copy, set a different port in the same PowerShell window:

```powershell
$env:PORT = "3001"
npm start
```

Open `http://localhost:3001`. To stop a running app, press `Ctrl+C` in the terminal where that app was started. `npm run start:clean` checks whether the port is occupied and reports the listener without terminating it.

Startup batches subject-sheet reads to reduce Google Sheets API quota usage. If Google reports a read-quota limit, the app retries with increasing delays; after repeated recent restarts, wait about a minute for the per-minute quota window to reset, then restart the app once.

Run the authentication integration/security checks with `npm test`.

Open `http://localhost:3000`. Students use the QR URL generated by the dashboard. For local phone testing, the phone must be on the same Wi-Fi network as the computer; if the link still cannot connect, check that Windows Firewall allows inbound connections to Node.js on the app's port. For students on another network, deploy the app over HTTPS and set `APP_URL` to that public URL.

On a fresh database, the first admin can register from the signup page without a setup key and must verify the email OTP before login. Starting with that first signup, public registration is closed; signed-in admins can use **Manage admins** to invite additional email addresses. Invitees complete signup with their own name, email, password, and a verification code sent to that email. Each account receives the `ADMIN` role from the backend—there is no role selector. Pending-signup code resending is available from the signup page after entering the registered email.

Admin credentials, OTPs, and persistent login sessions are stored in the SQLite database, never in Google Sheets. Passwords use bcrypt; OTPs are hashed, expire after 10 minutes, and allow at most five attempts. OTP requests have a one-minute resend cooldown and rate limits. Admins can view accounts and activate/deactivate other admins; the last active verified admin cannot be deactivated. The application imports a previous `.admin-account.json` account into SQLite on startup when present.

Email is sent through one backend service with reusable, responsive HTML and plain-text versions for verification OTPs, invitations, welcome messages, password resets, account status changes, attendance alerts, and attendance summaries. Admins enter an invitee's name and email. Students may enter an email during QR check-in; the address is saved in the Students sheet and used for present/absence notices. Failed attendance email delivery does not undo an already-recorded attendance event and is explicitly reported in the response/UI. From the dashboard, admins can send a summary to the roster email; counts are calculated from attendance records in the configured subject sheets. Never place SMTP secrets in frontend variables.

## Attendance lifecycle

1. Instructor selects a subject and optional batch scope, then generates a QR.
2. The QR is valid for 30 minutes and cannot be edited without invalidating its signature.
3. Students submit a name, batch, and optionally an email for updates. The server maps the course and writes `Present`.
4. Instructor clicks **Close session and mark absences**. Students in the session scope without a mark receive `Absent` when attendance was recorded for that class. If nobody was marked, the date remains blank. Sundays and configured holidays cannot be used to record attendance and are excluded from totals.
5. The `Percentage` tab is rebuilt from present and absent rows. Blank dates and holidays do not count toward total classes.
6. After marking attendance, students can check their own subject attendance. The lookup uses the subject matrix date columns, excludes future dates, and matches by name plus batch.

Close a session only after the class is finished. Past records are not exposed through correction controls. Google Sheets itself should be restricted to trusted administrators.

Student device linking is based on the browser's persistent local-storage token and the entered student name plus batch. Clearing browser storage, using a private browsing session, or changing browsers can make a device appear new; this is a browser limitation, not a hardware-identity check.

## Deploy publicly on Render

The development address (for example, `192.168.x.x`) is private to your local network. To let phones on other networks scan attendance QR codes, deploy the app to a public HTTPS host. This repository includes a `render.yaml` blueprint that creates one Render web service and mounts persistent storage for the SQLite database and device bindings. A paid Render service plan is required for the persistent disk; do not use an ephemeral filesystem for the database.

1. Push this repository to GitHub and create a new Blueprint on Render using that repository and its `render.yaml`.
2. During setup, provide `GOOGLE_SPREADSHEET_ID` and `GOOGLE_SERVICE_ACCOUNT_JSON`. The service account must have Editor access to the spreadsheet. In Render, enter the service-account JSON as one value; keep it private.
3. Wait for deployment, then open the service's public `https://<service-name>.onrender.com` URL and complete first-admin signup and email verification. Configure the optional SMTP settings if OTP and attendance email delivery is needed.
4. If Render did not set `APP_URL`, it can be left unset: QR links use the incoming public host and HTTPS forwarded by Render. Alternatively set it to the exact public HTTPS service URL. Generate a fresh QR after deployment; QR sessions are held in memory and do not survive a service restart.
5. Keep the service to one running instance. This app uses in-memory active QR sessions and process-local rate limits, and it stores SQLite plus device-binding locks on the attached persistent disk. Back up the disk data regularly.

For any production host, use HTTPS, keep `JWT_SECRET` private, and keep both `DATABASE_URL` and `DEVICE_LOCKS_PATH` on persistent storage. Never commit `.env` or place service-account credentials in `public/`. The admin cookie is HttpOnly, SameSite=Strict, signed, and expires after eight hours.

## Smoke test checklist

- Create the first admin without a setup key, verify the email OTP, then sign in and reject an incorrect password.
- Invite a second admin, complete signup, and verify both admins can log in independently.
- Reject duplicate email signup, wrong/expired OTPs, unverified login, and deactivated admin login.
- Confirm API signup cannot set a role and unauthenticated admin management requests are rejected.
- Reset the password with an email OTP and confirm the previous password no longer works.
- Generate a QR for a subject and submit a valid student.
- Submit the same student again and confirm the duplicate message.
- Try `Rahul123`, `Rahul@`, and `P11`; all must be rejected.
- Close a scoped session and verify missing roster students receive `Absent`; when roster emails and SMTP are configured, verify absence notifications.
- Enter a student email at check-in and verify the attendance confirmation arrives at that address. From the dashboard, send that student's summary and verify counts against the subject sheets.
- Add a student with an email to the roster, close a session where they were not present, and verify an absence email with the selected subject/date/faculty. `npm test` checks the dynamic HTML/text template values without requiring external SMTP credentials.
- Verify the Percentage tab reports `17 / 20 = 85.00%` for a 17-present, 3-absent case.
- Wait for or temporarily set `QR_MINUTES=1` and confirm expired QR submission is rejected.
